MPI/HDF5 file I/O ​

save_hdf5/load_hdf5! write and read Field data to/from a single shared HDF5 file, using the Grid's Cartesian topology to place each rank's block at its correct offset. This is an optional extension: it activates only once HDF5 is loaded alongside HaloGrids.

julia
using HaloGrids
using HDF5   # loads HaloGridsHDF5Ext

t = topology((0, 0))
g = grid(t, (66, 66))
f = field(rand(66, 66); halowidths=(1, 1))

save_hdf5(g, f, "state.h5")

loaded = field(zeros(66, 66); halowidths=(1, 1))
load_hdf5!(g, loaded, "state.h5")
update_halo!(g, loaded)   # repopulate the halo cells load_hdf5! left untouched

Calling save_hdf5/load_hdf5! without using HDF5 raises a clear error naming the missing dependency, rather than a bare MethodError — see save_hdf5/load_hdf5! in the API reference.

Halo cells are not stored ​

Just like gather!, this extension is explicit about halos, but in the opposite direction: rather than requiring the caller to strip them, save_hdf5 strips them for you. A cell is written only if no neighbor also owns a copy of it — the outer halowidths[d] cells on a side with a real neighbor are skipped, while the same-width strip on a non-periodic domain boundary (which has no neighbor, so is genuine, uniquely-owned data, not halo) is written normally. This keeps the file's per-field dataset exactly nglobal-shaped, with no duplicated cells anywhere.

The consequence: after load_hdf5!, halo cells that do have a real neighbor are left exactly as they were in the caller's array (typically stale or zero) — they were never saved, so there is nothing to load. Call update_halo! afterward to repopulate them from the now-loaded neighbor data, as in the example above.

Multiple fields in one file ​

julia
u = field(zeros(66, 66); halowidths=(1, 1))
v = field(zeros(66, 66); halowidths=(1, 1))
save_hdf5(g, (u, v), "state.h5"; names=("u", "v"))

u2 = field(zeros(66, 66); halowidths=(1, 1))
v2 = field(zeros(66, 66); halowidths=(1, 1))
load_hdf5!(g, (u2, v2), "state.h5"; names=("u", "v"))

names defaults to ("field1", "field2", ...) by position when omitted, so a save/load pair that both omit it agree on the dataset labels without having to repeat them. Field names must be unique within a file/group.

Restart with a different number of ranks ​

Pass repartition=true to read a checkpoint using a different rank count or Cartesian process-grid shape. Each reader rank loads its own portion directly from the saved global dataset. Existing schema 0.2.0 files work unchanged.

For example, save a periodic 64-by-64 domain using four ranks:

julia
t = topology((2, 2); periods=(true, true))
g = grid(t, (34, 34))  # 32 owned cells plus two halo cells per dimension
f = field(rand(34, 34))
save_hdf5(g, f, "state.h5")

In a separate run with eight ranks, load the same file:

julia
t = topology((4, 2); periods=(true, true))
g = grid(t, (18, 34))
f = field(zeros(18, 34))
load_hdf5!(g, f, "state.h5"; repartition=true)
update_halo!(g, f)

Construct the destination grid and fields before loading. For each dimension, the required local size is (saved_nglobal - 2*hw*!periodic) ÷ topology_dims + 2*hw; the division must be exact. Halo widths, element types, global shapes, and periodicity must match the saved fields. Nonperiodic physical boundary strips remain part of the saved global domain. Only uniform per-rank decompositions are supported; multiple fields must all be compatible with the destination grid's local size.

repartition=true also works with field tuples, names, and group. Neighbor halos remain untouched during loading: call update_halo! before using them. HDF5 I/O still requires CPU arrays.

The runnable checkpoint_restart.jl example saves a position-dependent field and checks every cell after restart. From an environment with HaloGrids, MPI and HDF5 (for example ]dev this repository, then ]add MPI HDF5) and an MPI launcher matching MPI.jl, run:

sh
mpiexec -n 4 julia --project=<env> examples/checkpoint_restart.jl save state.h5
mpiexec -n 2 julia --project=<env> examples/checkpoint_restart.jl load state.h5
mpiexec -n 8 julia --project=<env> examples/checkpoint_restart.jl load state.h5

Validation ​

load_hdf5! checks a dataset's saved metadata (schema version, topology dimensions, nlocal, nglobal, halo widths, element type) against the Grid/Field requesting the load before touching any payload, and raises a plain error(...) naming the saved and requested values on the first mismatch — most commonly a different process-grid shape or nlocal than the file was written with. With repartition=true, topology dimensions and local size may differ; global shape, halo widths, element type, and saved periodicity are still checked, as is the dataset shape. Periodicity is recovered from the saved global and local geometry, including for existing files. save_hdf5 similarly refuses to reuse an existing dataset name in an existing file (append a distinct name/names, use a distinct group, or start from a fresh file with mode="w", the default).

Why every rank still calls these together ​

There is no parallel-HDF5 build to make a genuinely simultaneous, collective multi-rank write meaningful here (HDF5.has_parallel() is false for the ordinary HDF5_jll-backed install this package's weak dependency resolves to). save_hdf5still requires every rank in the grid's topology to call it together — internally, ranks take turns, in order, opening the shared file, writing only their own hyperslab, and closing it before the next rank's turn, synchronized byMPI.Barrier/MPI.Allreduce— so it remains collective in the sense that matters (every rank must call it, and the on-disk result depends on all of them), just not simultaneous. Reads are not serialized this way: concurrent read-only access to the same file from multiple processes is ordinary, safe behavior even without a parallel-HDF5 build, so every rank inload_hdf5! opens and reads the file independently.

This also means a call that raises an error must be treated as having failed on every rank together, even though (depending on which rank's turn was in progress) not every rank observes the identical exception object — don't rely on save_hdf5/load_hdf5! errors being non-fatal on a subset of ranks.

With the default mode="w", the file is written as path * ".tmp" and rank 0 renames it to path only after every rank has written. A save that is killed or fails partway leaves any previous file at path intact (and a stale .tmp beside it). Other modes, such as "r+", write into path directly, so an interrupted save there can leave blocks unwritten.

CPU arrays only ​

Both functions require every field's array to be a StridedArray (Array, or a contiguous SubArray/ReshapedArray/PermutedDimsArray of one) — i.e. ordinary, host-addressable memory. A CuArray/ROCArray field must be staged to the host first:

julia
save_hdf5(g, field(Array(gpu_field.data); halowidths=gpu_field.halowidths), path)
