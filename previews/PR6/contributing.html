Development and documentation ​

Julia checks ​

From the repository root:

sh
julia --project=. -e 'using Pkg; Pkg.instantiate()'
julia --project=. --startup-file=no test/test_field.jl
julia --project=. --startup-file=no test/runtests.jl

The full driver starts its own MPI subprocesses at 1, 2, 4, and 8 ranks. Threaded packing checks run separately with four Julia threads at 1 and 2 ranks. Run the driver directly, without an outer MPI launcher. Allow enough process slots for eight ranks, or run focused files with an appropriate MPI.jl launcher while developing.

Continuous integration ​

GitHub Actions runs on pushes, pull requests, and manual dispatches. The Julia jobs test Julia 1.9 and the latest stable 1.x release on Linux, using the full MPI and threaded test driver and the quickstart example. Dependencies are resolved from Project.toml in each job rather than the development manifest. The CPU driver is invoked directly; the CUDA/AMDGPU extensions are implemented and tested locally (see the package's REDESIGN_PLAN.md) but CI does not install their test extras (the root [extras]/[targets], installed by Pkg.test()) — doing so would add real, un-opted-into time and network cost to every job for runners that have no GPU to test against anyway. test/runtests.jl detects this and prints a one-line skip for the GPU test files rather than failing.

A separate job builds this site with docs/make.jl. Documenter's own link and docstring checks run as part of that build.

Work on this site ​

This site is built with Documenter.jl and rendered to HTML by DocumenterVitepress.jl, which drives VitePress internally — no repository-level Node.js setup is needed, since DocumenterVitepress manages its own Node dependencies. Only Julia is required. From the repository root:

sh
julia --project=docs -e 'using Pkg; Pkg.instantiate()'
julia --project=docs docs/make.jl

This writes the site to docs/build/1 (see DocumenterVitepress's own docs for why the numbered subfolder: locally it is always 1, since a local build is neither a dev, version, nor PR-preview build). Preview it with LiveServer.jl:

julia
using Pkg; Pkg.activate("docs"); Pkg.add("LiveServer")
using LiveServer
LiveServer.serve(dir = "docs/build/1")

Or, for an automatically rebuilding preview while editing:

julia
using LiveServer
LiveServer.servedocs(buildfoldername = "build/1")

The quickstart, halo-exchange overlap, ParallelStencil boundary-width, and coordinate-helper pages embed examples/quickstart.jl, examples/hide_communication.jl, examples/parallelstencil_overlap.jl, and examples/diffusion3D.jl directly via @eval blocks that read the file at build time, so edits to their executable source also update the page. The API reference (docs/src/api.md) is built entirely from @docs blocks pulling docstrings out of src/, so it cannot drift from the implementation the way a hand-written signature list can — update the docstring, not the page, when a public signature changes.

Internal validation and backend hooks ​

The following implementation hooks are documented for contributors. They are not exported public API; array backends override the dispatch hooks through package extensions.

HaloGrids.check_fields Function
julia
check_fields(grid::Grid{N}, fields::NTuple{M,Field}) where {N,M}

Validate a batch of fields against the Grid they are about to be exchanged on. Raises a plain error(...) (no custom exception hierarchy, matching the old package's actual hot-path convention) describing the first problem found:

  • a field's dimensionality is smaller than the grid's, or its size disagrees with grid.nlocal in the grid's own leading dimensions,

  • two fields in the same call alias the same underlying array.

A field may have more dimensions than the grid (e.g. the CellArrays extension's batched B=0 path, src/CellArraysExt/halo_exchange.jl, wraps a CellArray's cell-component axis as one extra trailing field dimension): any dimension beyond the grid's own N is never checked against grid.nlocal and is only ever touched by the exchange machinery (sendrange/recvrange/halo_length in halo_exchange.jl, which already loop over a field's own ndims, not the grid's) if it is explicitly named in a call's dims argument — which nothing in this package does for a dimension beyond N, since dims is itself validated against the grid's N (check_dims, below). A field with fewer dimensions than the grid is still rejected, same as before.

HaloGrids.pack_target Function

GPU dispatch seam for pack/unpack and MPI-transport staging, overridden by the CUDA/AMDGPU package extensions (ext/HaloGridsCUDAExt.jl, ext/HaloGridsAMDGPUExt.jl) and resolved by ordinary multiple dispatch on the array type — a GPU extension adds methods for AnyCuArray/AnyROCArray and nothing else needs to change at the call sites in halo_exchange.jl. Unlike the old package, no runtime "is the extension loaded" flag is needed at all.

GPU-specific cached state (streams, device buffers) lives behind the Ref{Any} gpu_cache slot owned by the Grid's ExchangeCache (see exchange_cache.jl), never module-global.

For a plain CPU AbstractArray, pack_target/unpack_source are literally sendbuf/recvbuf (the same host buffer packing has always used) and stage_send!/stage_recv! are no-ops, so these four defaults reproduce today's CPU behavior exactly, at zero extra runtime cost once specialized per concrete array type.

For a GPU array, a device-resident buffer pool (owned by the grid's ExchangeCache.gpu_cache, never module-global) is the actual pack/unpack target/source — pack!/unpack! (halo_exchange.jl) then run entirely on device via copyto!/view, unmodified, since GPUArrays.jl already gives device arrays a generic strided copyto!. stage_send!/stage_recv!are the plain contiguous device<->host copies that bridge that device buffer to the hostsendbuf/recvbufMPI actually sends/receives from: MPI transport itself never becomes GPU-aware, only pack/unpack does. This split is also the documented seam for a future CUDA-aware-MPI path (makestage_send!/stage_recv!no-ops and letpost_isend!/post_irecv! operate on the device buffer directly) — not implemented here since it requires a CUDA-aware MPI build to validate, which this project's local Microsoft MPI is not.

Deployment ​

docs/make.jl ends with a DocumenterVitepress.deploydocs call targeting the gh-pages branch of this repository. It only actually pushes when run in a CI job on a qualifying push (see DocumenterVitepress's deployment docs); running make.jl locally only ever produces the local docs/build/1 output above. Enabling live deployment additionally requires GitHub Pages to be configured for this repository and, if deploying across repository permissions rather than the default GITHUB_TOKEN, a DOCUMENTER_KEY deploy key — see Documenter.jl's hosting documentation for the general mechanism (DocumenterVitepress's deploy step follows the same key/branch conventions).
